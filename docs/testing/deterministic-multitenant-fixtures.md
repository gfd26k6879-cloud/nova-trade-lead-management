# Deterministic multitenant fixtures

The browser-safe canonical fixture catalog uses fixed synthetic IDs only. It creates two tenants, two active workspaces per tenant, every launch role, and pending, suspended, and disabled membership cases. The catalog also exposes exactly two tenant-owned workspace look-alike record IDs for unit, integration, and E2E selectors.

The full fixture includes approved and revoked support-grant history and is rollback-only through `withCanonicalTenantFixtures`; its transaction also removes callback writes. Committed tests must use `setupCanonicalTenantCoreFixtures` and `cleanupCanonicalTenantCoreFixtures`. That cleanup-safe core retains both tenants, both workspaces per tenant, every launch role, lifecycle memberships, policies, and both look-alike records, but creates no immutable support history. Core cleanup deletes only its exact canonical child and parent IDs in foreign-key-safe order, is idempotent, preserves unrelated rows, and never drops, disables, bypasses, or changes support-history guards.

`tenant-fixtures-postgres.test.ts` is opt-in. Set `Q002_POSTGRES16=1` and `Q002_POSTGRES_ADMIN_URL` to a loopback PostgreSQL 16 administrative URL. Run it against an immutable pinned PostgreSQL 16 image and retain that digest in the validation evidence. The test refuses non-loopback targets and non-16.x servers, creates a uniquely named disposable database, applies the tracked migration chain except the two named pg_net/pg_cron/Vault runtime migrations, and uses a bounded postgres.js `DbClient` adapter with the real tenant repository. It runs committed core setup and exact-ID cleanup twice, preserves unrelated rows and schema protections, verifies rollback-only full support history, then force-drops the disposable database.
